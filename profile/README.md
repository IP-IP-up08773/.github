<h2>「一店一 IP」不是一句口号，是三张表</h2>
<p>很多团队知道规则，但执行不下去。原因不是不愿意做，而是没有可操作的载体。落地的关键是把规则变成三张表：店铺台账、资源绑定表、环境清单。</p>
<p>三张表填满，一店一 IP 就从「理念」变成了「可检查的状态」。缺一张，执行就会走样。</p>

<h2>第一张：店铺台账</h2>
<p>记每个店铺的基本信息：店铺名、所属市场、注册时间、当前状态、负责人。这张表是主索引，所有后续信息都挂在它下面。</p>
<p>负责人一栏别省。多店铺运营里最常出的事是「这个店谁在管」，出问题时找不到人。</p>

<h2>第二张：资源绑定表</h2>
<p>记每个店铺绑定的地址：地址标识、归属地区、独享或共享、绑定开始时间、是否曾更换。这一列「是否曾更换」很关键，它记录了历史，出问题时可回溯。</p>
<p>这张表要能回答两个问题：这个店铺用的是哪条地址，这条地址有没有被别的店铺用过。第二个问题最容易失控。</p>

<h2>第三张：环境清单</h2>
<p>记每个店铺的环境配置：浏览器环境标识、时区、语言、解析设置、设备参数。这张表的作用是检查「有没有两个环境长得太像」。</p>
<p>定期对比一次是关键。凭感觉判断「应该不一样」，实际可能因为套用了同一个模板而高度相似。</p>

<h2>设置流程七步</h2>
<p>第一步，建店铺记录。第二步，采购并验收一条独享静态地址。第三步，在资源绑定表里登记绑定关系。第四步，建立独立环境并登记参数。</p>
<p>第五步，在环境里配置网络接入。第六步，验证出口与解析。第七步，正式登录运营。七步顺序不要跳，尤其是第六步。</p>

<h2>配置细节：浏览器环境</h2>
<p>每个店铺一个独立环境，不共用配置。时区、语言、地区设置与地址一致。分辨率与设备参数尽量做到彼此有差异，避免多环境高度雷同。</p>
<p>不要把多个店铺放在同一个浏览器里切换。同一个浏览器开多个配置，某些底层参数仍然共享，指纹容易串。</p>

<h2>配置细节：网络接入</h2>
<p>代理配置写在环境里，而不是系统全局。这样切换店铺不影响其他环境。填好后先在环境内测一次出口地址，确认走的是预期线路。</p>
<p>解析也要在环境内确认。很多工具会把解析请求绕过代理，导致真实位置暴露。配完用检测工具看一次解析来源。</p>

<h2>验证与上线</h2>
<p>三查：出口地址对、解析来源一致、环境参数与地区匹配。三查都过再登录，不要在没验证的情况下先登录再补。</p>
<p>首次登录后观察一段时间。如果出现频繁的额外验证，说明环境可能有问题，先排查再继续操作。</p>

<h2>变更管理</h2>
<p>换地址、换环境、换设备，三种变更都要在表里留记录，并注明原因。变更之后要重新跑一遍三查。</p>
<p>最常见的隐患是「变更没记录」。三个月后没人记得某个店铺换过地址，出问题时无法判断是不是变更引起的。</p>

<h2>常见问答</h2>
<h3>一定要独享地址吗？</h3>
<p><strong>答：</strong>主力店铺建议独享。共享地址会被同段他人影响。</p>
<h3>一个店铺能用两个环境吗？</h3>
<p><strong>答：</strong>不建议。同一店铺在不同环境登录，本身就是一个相似度断点。</p>
<h3>店铺多了表怎么管？</h3>
<p><strong>答：</strong>用表格工具即可，关键是有没有人维护。工具不重要，更新及时才重要。</p>
<h3>换地址要重新配环境吗？</h3>
<p><strong>答：</strong>要。绑定关系变了，环境里的配置与验证都要重做。</p>
